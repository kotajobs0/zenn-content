こんにちは。ITフィールドセールスをしている長井洸太です。

前回の記事では「プロンプト設計はAPI設計と同じ」という話を書きましたが、今回はもう少し実践寄りに、実際のJavaコードをClaudeにレビューしてもらった記録を残します。

---

## 気づきの出発点（問題意識）

セールスとして日々Javaエンジニアと話していると、こんな会話によく出会います。

> 「このPR、レビューで差し戻されました」
> 「設計レビューで指摘されて、想定より工数が伸びそうです」

こういう時、正直なところ「その指摘が妥当なのかどうか」を自分の頭では判断できませんでした。指摘された側の説明を聞くしかなく、レビューの中身そのものに踏み込めない。

これでは、見積もりの相談を受けても「なぜ時間がかかるのか」を本当の意味で理解できません。

そこで、実際に問題のあるJavaコードを用意し、Claudeにレビューしてもらうことで、「プロのコードレビューは何を見ているのか」を自分の目で確認してみることにしました。

---

## AIと対話した内容

用意したのは、わざと複数の問題を仕込んだ在庫管理用の小さなJavaクラスです。

```java
public class InventoryService {

    private FileInputStream stream;

    public int checkStock(String itemId) {
        try {
            stream = new FileInputStream("stock/" + itemId + ".txt");
            int value = stream.read();
            return value * 100;
        } catch (Exception e) {
            System.out.println("error");
            return -1;
        }
    }

    public void updateStock(String itemId, int amount) {
        int current = checkStock(itemId);
        current = current + amount;
        System.out.println(current);
    }
}
```

これをそのままClaudeに渡し、レビューを依頼しました。

```
私：「あなたはJavaのシニアエンジニアです。以下のコードを
セキュリティ・保守性・例外処理の観点でレビューしてください。
問題点を重要度（Critical / Major / Minor）付きで箇条書きに
してください。」

Claude：
【Critical】
・FileInputStream をクローズしていません。try-with-resources
  を使わないと、ファイルディスクリプタがリークし続けます。

・checkStock 内の catch (Exception e) が広すぎます。すべての
  例外を握りつぶし、原因不明のまま -1 を返しているため、呼び出し
  側は「在庫がない」のか「エラーが起きた」のか区別できません。

【Major】
・itemId をそのままファイルパスに結合しています。itemId に
  "../" のような文字列が渡された場合、意図しないファイルに
  アクセスできてしまう可能性があります（パストラバーサル）。

・value * 100 の 100 の意味がコードから読み取れません。
  マジックナンバーとして定数化するべきです。

・エラー処理に System.out.println を使っています。ログレベルの
  制御ができず、本番運用でノイズになります。

【Minor】
・updateStock が checkStock の戻り値を再利用していますが、
  checkStock がエラー時に -1 を返す仕様のため、amount を
  加算すると不正な在庫数になり得ます。
```

## そこから得た結論・整理

出てきた指摘を分類すると、プロのレビューが見ている観点は大きく4つに整理できました。

| 観点 | 今回のコードで指摘された内容 |
|------|------------------------------|
| リソース管理 | `FileInputStream` を閉じていない（リーク） |
| 例外処理 | `catch (Exception e)` が広すぎて原因が握りつぶされる |
| セキュリティ | ユーザー入力をそのままファイルパスに使っている（パストラバーサル） |
| 保守性 | マジックナンバー・`System.out.println`によるログ管理の欠如 |

「バグがあるかどうか」だけでなく、**「将来この呼び出し側が誤動作する余地がないか」まで見ている**のが印象的でした。特にパストラバーサルの指摘は、セールスの自分には全く見えていない観点で、こういう視点がエンジニアの「レビューに時間がかかる理由」なのだと腑に落ちました。

## 実務・現場への応用

このレビュー結果を見てから、エンジニアとの会話で聞き方が変わりました。

- 「差し戻された」と聞いたら、「セキュリティ・例外処理・保守性のどれに関する指摘でしたか」と聞けるようになった
- 見積もり相談で「なぜその工数か」を聞くとき、「例外処理をちゃんと設計する時間も含まれていますか」と踏み込めるようになった
- エンジニア同士の会話で出てくる「リーク」「握りつぶす」といった言葉の意味が、実感を伴って理解できるようになった

技術を代わりに書けるようにはなりませんが、**エンジニアが何にこだわって時間を使っているかが分かる**ようになったのは、セールスとして地味に大きな変化でした。

---

## やってみてわかったこと

### AIのレビューは「観点の抜け漏れチェック」に強い

今回のコードは意図的に問題を仕込みましたが、Claudeは一度のレビューで4つの観点すべてを拾ってきました。人間のレビューだと観点によって得意不得意がありますが、AIは横断的に一通りチェックしてくれる印象です。

### 「なぜダメか」の説明が言語化の練習になる

指摘そのものよりも、「なぜそれが問題なのか」という説明文が、非エンジニアが技術を理解する教材として優秀でした。エンジニアに直接聞くと省略されがちな前提が、AIの説明には丁寧に書かれています。

### レビュー内容を鵜呑みにしないことも大事

今回は分かりやすく問題を仕込んだコードだったので指摘が的確でしたが、実際の複雑なコードベースでは、AIが文脈を誤解して的外れな指摘をすることもあると聞きます。「AIの指摘＝正解」ではなく、あくまで一つの視点として使うのが実務では良さそうです。
