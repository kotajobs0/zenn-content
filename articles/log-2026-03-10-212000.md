## 1. 若手からの相談（と、ありがちな課題）

ある日、入社2年目の若手エンジニアA君から相談を受けました。

**A君:** 「[あなたの名前]さん、今、レガシーなコードのリファクタリングを担当しているんですが、どこから手を付けていいか分からなくて…。メソッドが長すぎるし、同じような処理が色んなところに散らばっていて、正直、読むのも辛いです…。」

…はい、よくある話です。彼が抱えている問題は、多くの若手エンジニアが直面するものです。

*   **巨大なメソッド:** 単一のメソッドが長すぎて、何をしているのか理解しにくい。
*   **コードの重複:** 同じような処理が複数の箇所に存在し、修正時に漏れが発生しやすい。
*   **低い凝集度:** クラスやメソッドが複数の役割を担っており、変更の影響範囲が広くなりやすい。

## 2. シニアのあなたの思考（リファクタリングの戦略）

A君の相談を受けて、私は以下の点を意識しながら、リファクタリングの戦略を立てることにしました。

1.  **小さな変更から始める:** 一度に大きな変更を加えるのではなく、小さな変更を繰り返すことで、リスクを最小限に抑える。
2.  **テスト駆動開発 (TDD) を意識する:** リファクタリング前にテストコードを作成し、変更によって既存の機能が壊れないことを保証する。
3.  **共通処理を抽出する:** 重複しているコードを共通化し、再利用性を高める。
4.  **メソッドやクラスの責務を明確にする:** メソッドやクラスが単一の役割を担うように設計し、凝集度を高める。
5.  **可読性を重視する:** 変数名やメソッド名を分かりやすくし、コメントを適切に追加する。

## 3. AI (Gemini) への指示

今回は、A君が担当しているコードの一部（割引計算処理）を例に、Geminiにリファクタリングの提案をしてもらうことにしました。

**私:** 「以下のJavaコードをリファクタリングしてください。特に、処理が長すぎるため、メソッド分割と共通処理の抽出を行い、可読性を向上させてください。TDDの観点から、テストコードの提案もお願いします。割引率の計算ロジックは、顧客の属性（年齢、購入回数）に基づいて動的に決定されます。」

```java
public class DiscountCalculator {

    public double calculateDiscountedPrice(double originalPrice, int customerAge, int purchaseCount) {
        double discountRate = 0.0;

        if (customerAge >= 60) {
            discountRate = 0.15; // 高齢者割引
        } else if (purchaseCount >= 10) {
            discountRate = 0.10; // リピーター割引
        } else if (purchaseCount >= 5 && customerAge >= 20) {
            discountRate = 0.05; // 若年層リピーター割引
        } else {
            discountRate = 0.0;
        }

        double discountedPrice = originalPrice * (1 - discountRate);
        return discountedPrice;
    }
}
```

**補足:**

*   Geminiに具体的なコードと課題を伝えることで、より実践的なアドバイスを得られるようにしました。
*   TDDの観点も盛り込むことで、テストの重要性を意識してもらうようにしました。

**リファクタリング後のコード:**

```java
public class DiscountCalculator {

    public double calculateDiscountedPrice(double originalPrice, int customerAge, int purchaseCount) {

        return originalPrice * (1 - discountRate);
    }

            return 0.10; // リピーター割引

            return 0.05; // 若年層リピーター割引
        } else {
            return 0.0;
        }
    }

    private boolean isSenior(int customerAge) {
        return customerAge >= 60;
    }

    private boolean isFrequentCustomer(int purchaseCount) {
        return purchaseCount >= 10;
    }

    private boolean isYoungFrequentCustomer(int customerAge, int purchaseCount) {
        return purchaseCount >= 5 && customerAge >= 20;
    }
}
```

## 5. Java vs C# 実装比較

Geminiが提案してくれたリファクタリング後のコードを、Java 21とC# 12で比較してみましょう。今回は、簡潔さを重視し、レコード (Java) / レコード型 (C#) を使って、割引率を表現してみます。

**Java 21 (レコードを使用):**

```java
public class DiscountCalculator {

    record Discount(double rate, String reason) {}

    public double calculateDiscountedPrice(double originalPrice, int customerAge, int purchaseCount) {
        Discount discount = calculateDiscount(customerAge, purchaseCount);
        return originalPrice * (1 - discount.rate());
    }

    private Discount calculateDiscount(int customerAge, int purchaseCount) {
        if (isSenior(customerAge)) {
            return new Discount(0.15, "高齢者割引");
        } else if (isFrequentCustomer(purchaseCount)) {
            return new Discount(0.10, "リピーター割引");
        } else if (isYoungFrequentCustomer(customerAge, purchaseCount)) {
            return new Discount(0.05, "若年層リピーター割引");
        } else {
            return new Discount(0.0, "割引なし");
        }
    }

    private boolean isSenior(int customerAge) {
        return customerAge >= 60;
    }

    private boolean isFrequentCustomer(int purchaseCount) {
        return purchaseCount >= 10;
    }

    private boolean isYoungFrequentCustomer(int customerAge, int purchaseCount) {
        return purchaseCount >= 5 && customerAge >= 20;
    }
}
```

## 6. 若手への一言（明日から使えるお作法）

今回のリファクタリングの例から、明日から使えるお作法として、以下の３つを意識してみてください。

1.  **「メソッドは短く、クラスは小さく」の原則を意識する:** 長すぎるメソッドや責務が多すぎるクラスは、保守性を著しく低下させます。
2.  **テストコードを必ず書く:** リファクタリングによって既存の機能が壊れないことを保証するためには、テストコードが不可欠です。
3.  **積極的にAIを活用する:** AIは、コードの改善点を見つけたり、新しい技術を学んだりする上で、強力なツールとなります。ただし、AIの提案を鵜呑みにするのではなく、自分で理解し、判断することが重要です。

リファクタリングは地道な作業ですが、長期的に見ると、開発効率や品質を大きく向上させる効果があります。今回の記事が、皆さんのコードがより美しく、より保守性の高いものになる一助となれば幸いです。頑張ってください！
