こんにちは。エンジニアをしている長井洸太です。

前回の記事「[Javaエンジニアが初めてClaudeを使うときに最初に知っておくべき3つのこと](https://zenn.dev/kotajobs0/articles/2026-06-29-java-claude-basics)」を読んでくれた方から、こんな質問をもらいました。

> 「サンプル通りにAPIを叩けたのはいいんですが、プロンプトを変えるたびに出力の質がバラつくんです。何が悪いんでしょうか」

これ、すごく本質的な質問だと思っています。今回はこの「プロンプトが安定しない問題」について、Javaエンジニアの感覚で整理してみます。

---

## 気づきの出発点（問題意識）

Javaを書いている人にとって、こういうメソッドは怖くて書けません。

```java
// 引数の型も個数も決まっていないメソッド
public Object doSomething(Object... args) {
    // 中で何が起きるか、呼び出し側からは予測できない
}
```

型がない、契約がない、何が返ってくるか分からない。こんなコードはレビューで即差し戻されます。

でも、多くの人が書いているプロンプトは、実はこれに近い状態です。

```
このコードをレビューして。
```

これだけ投げて、「なんで毎回微妙に違う回答が返ってくるんだろう」と悩む。よく考えると当然で、**入力の契約を決めていないのだから、出力の契約も決まらない**わけです。

---

## AIと対話した内容

このモヤモヤをそのままClaudeにぶつけてみました。

```
私：「プロンプトの出力が安定しません。Javaエンジニア的に理解する
にはどう捉えたらいいですか？」

Claude：「プロンプトは自然言語で書かれたAPIの呼び出しだと考える
と分かりやすいです。Javaのメソッドが『引数』『戻り値』『例外処理』
の3つで契約を明示するように、プロンプトも次の3つを明示すると
出力が安定します。

1. 引数（何を渡すか）：入力データの種類・形式・前提条件
2. 戻り値（何が返るか）：出力のフォーマット・粒度・文字数
3. 例外処理（想定外にどう対応するか）：情報不足や該当なしの場合
   の振る舞い

Javaのメソッドで例外処理を書き忘れると本番で予期しない挙動が
起きるのと同じで、プロンプトで例外ケースを指示し忘れると、
入力が想定外だったときにAIが『それっぽい回答』を作ってしまい、
結果がブレます。」
```

これを聞いて、「例外処理」という発想がすっぽり抜けていたことに気づきました。引数と戻り値は意識していても、想定外の入力にどう振る舞うかまでは指示していなかったのです。

---

## そこから得た結論・整理

Javaのメソッド設計とプロンプト設計を並べると、こう対応します。

| Javaのメソッド設計 | プロンプト設計 | 具体的にやること |
|-------------------|---------------|-----------------|
| 引数（Parameter） | 入力の定義 | 何を渡すか・形式・前提条件を明示する |
| 戻り値（Return） | 出力形式の定義 | フォーマット・文字数・粒度を固定する |
| 例外処理（Exception） | エッジケースの指示 | 情報不足・該当なしの場合の振る舞いを決める |

実際のプロンプトに落とすとこうなります。

```
# 例外処理を書いていないプロンプト（△）
あなたはJavaのシニアエンジニアです。
以下のコードをレビューしてください。

[コード]
```

```
# 引数・戻り値・例外処理を明示したプロンプト（○）
あなたはJavaのシニアエンジニアです。

# 引数（入力の前提）
以下はJavaのメソッド1つ分のコードです。

# 戻り値（出力形式）
セキュリティとパフォーマンスの観点で問題点を箇条書き3点以内、
それぞれに改善案を1行で添えてください。

# 例外処理（想定外への対応）
コードが渡されていない、またはJavaのコードとして認識できない
場合は、指摘を作らず「コードが確認できませんでした」とだけ
返してください。

[コード]
```

後者は「コードが空だったらどうするか」まで決めているので、変な指摘を無理やり作られる事故が起きません。Javaで `null` チェックを書かずにNPEを踏むのと同じ構造の失敗を、プロンプト側でも防げるようになります。

## 実務・現場への応用

チームでプロンプトを使い回す場合、この3点セットをテンプレート化しておくと、属人化を防げます。

```
【役割】あなたは〇〇の専門家です。

【引数（入力の前提）】
- 対象：
- 形式：
- 前提条件：

【戻り値（出力形式）】
- フォーマット：
- 文字数・粒度：

【例外処理（想定外への対応）】
- 情報不足の場合：
- 該当なしの場合：
```

コードレビューでメソッドのシグネチャを見るように、プロンプトも「引数・戻り値・例外処理が揃っているか」をチェックする習慣をつけると、チーム全体の出力品質が安定します。

---

## やってみてわかったこと

### 「例外処理」の発想が一番抜けやすい

引数と戻り値は直感的に意識しやすいのですが、「想定外の入力が来たときどうするか」は後回しにされがちです。Javaで例外処理を書き忘れて痛い目を見た経験がある人ほど、この観点は刺さると思います。

### プロンプトのレビューはコードレビューと同じ感覚でできる

「この引数の定義は曖昧じゃないか」「戻り値の形式は決まっているか」という視点でプロンプトを読むと、普段のコードレビューの延長でチェックできます。特別なスキルというより、既存の設計思考の転用でした。
