#### 課題のコード例（Java / C# 共通）

まず、若手エンジニアさんが書いたであろう、課題のあるコードのイメージです。

```java
// Javaの例（C#も同様の構造）
public class OrderService {

    public double calculateFinalPrice(Order order, Customer customer) {
        double basePrice = order.getTotalPrice();
        double discount = 0.0;

        if (customer.isVip()) {
            discount = basePrice * 0.15; // VIP割引15%
        } else if (customer.isFirstTimeBuyer()) {
            if (basePrice > 5000) {
                discount = basePrice * 0.05; // 初回購入者で5000円以上なら5%
            } else {
                discount = basePrice * 0.02; // 初回購入者で5000円未満なら2%
            }
        } else if (order.hasPromoCode("SUMMER2024")) {
            discount = basePrice * 0.10; // 特定のプロモーションで10%
        } else {
            discount = 0.0;
        }

        return basePrice - discount;
    }
}

// 関連クラス（簡易版）
class Order {
    private double totalPrice;
    private String promoCode;

    public Order(double totalPrice, String promoCode) {
        this.totalPrice = totalPrice;
        this.promoCode = promoCode;
    }

    public double getTotalPrice() { return totalPrice; }
    public boolean hasPromoCode(String code) { return code.equals(promoCode); }
}

class Customer {
    private boolean vip;
    private boolean firstTimeBuyer;

    public Customer(boolean vip, boolean firstTimeBuyer) {
        this.vip = vip;
        this.firstTimeBuyer = firstTimeBuyer;
    }

    public boolean isVip() { return vip; }
    public boolean isFirstTimeBuyer() { return firstTimeBuyer; }
}
```

このコードの問題点として、主に以下の点が挙げられます。

*   **ネストが深い**: `if-else if` が多重にネストしており、処理の流れを追うのが難しいです。
*   **ビジネスロジックの散在**: 割引条件のロジックが全てこのメソッド内に記述されており、新しい割引が追加されるたびにこのメソッドを修正しなくてはなりません。
*   **マジックナンバー**: 割引率（0.15, 0.05など）が直接コードに埋め込まれており、意味が分かりにくく、変更しにくいです。
*   **単一責任の原則違反**: 割引計算ロジックと、最終価格決定ロジックが混在しています。

#### Java 21 を活用した改善例

Java 21では、**パターンマッチング for switch** や **レコード（Records）** などの機能が進化しており、このような複雑な条件分岐を簡潔に記述できるようになります。

```java
// Java 21 活用例
import java.util.List;
import java.util.function.BiFunction;

// レコードで顧客情報を表現。不変性が保証され、簡潔に書ける
record CustomerInfo(boolean isVip, boolean isFirstTimeBuyer) {}
// レコードで注文情報を表現
record OrderDetails(double totalPrice, String promoCode) {}

public class AdvancedOrderService {

    // 割引ルールを表現するインターフェース
    interface DiscountRule extends BiFunction<OrderDetails, CustomerInfo, Double> {}

    // 割引ルールを具体的なクラスとして定義（戦略パターン）
    static class VipDiscount implements DiscountRule {
        @Override
        public Double apply(OrderDetails order, CustomerInfo customer) {
            return customer.isVip() ? order.totalPrice() * 0.15 : 0.0;
        }
    }

    static class FirstTimeBuyerDiscount implements DiscountRule {
        @Override
        public Double apply(OrderDetails order, CustomerInfo customer) {
            if (customer.isFirstTimeBuyer()) {
                return order.totalPrice() * (order.totalPrice() > 5000 ? 0.05 : 0.02);
            }
            return 0.0;
        }
    }

    static class PromoCodeDiscount implements DiscountRule {
        private final String code;
        private final double rate;

        public PromoCodeDiscount(String code, double rate) {
            this.code = code;
            this.rate = rate;
        }

        @Override
        public Double apply(OrderDetails order, CustomerInfo customer) {
            return order.promoCode().equals(code) ? order.totalPrice() * rate : 0.0;
        }
    }

    // すべての割引ルールをリストで保持
    private final List<DiscountRule> discountRules = List.of(
            new VipDiscount(),
            new FirstTimeBuyerDiscount(),
            new PromoCodeDiscount("SUMMER2024", 0.10)
    );

    public double calculateFinalPrice(OrderDetails order, CustomerInfo customer) {
        // 各ルールを順番に適用し、最大の割引額を計算
        // ここでは最大割引を採用していますが、要件に応じて累積割引などに変更可能
        double totalDiscount = discountRules.stream()
                .mapToDouble(rule -> rule.apply(order, customer))
                .max()
                .orElse(0.0);

        return order.totalPrice() - totalDiscount;
    }
}
```

**改善点とJava 21のメリット:**

*   **単一責任の原則**: 各割引ルールが独立したクラス（`DiscountRule`の実装）として定義され、それぞれのクラスが自身の割引ロジックのみを担当します。これにより、新しい割引が追加されても、既存のコード（`calculateFinalPrice`メソッド）を修正することなく、新しいルールクラスを追加するだけで対応できるようになります（「オープン・クローズドの原則」）。
*   **可読性と保守性**: `calculateFinalPrice`メソッドは、割引ルールを適用する「 orchestrator（統括者）」としての役割に専念し、ビジネスロジックの詳細から解放されました。リスト化された割引ルールをストリームAPIで処理することで、何が起こっているかが一目で分かります。
*   **レコードの活用**: `CustomerInfo` や `OrderDetails` をレコードとして定義することで、ボイラープレートコード（ゲッター、セッター、`equals`, `hashCode`, `toString`）を大幅に削減し、簡潔かつ安全に値オブジェクトを扱えます。不変性も保証されます。
*   **関数型インターフェースの活用**: `BiFunction` を`DiscountRule` インターフェースのベースとして使うことで、より関数型プログラミングに近い記述が可能になり、ロジックがシンプルになります。

#### C# 12 を活用した改善例

C# 12でも、**プライマリコンストラクタ**や**コレクション式**、そして以前から強力な**LINQ**や**パターンマッチング**を活用することで、同様に洗練されたコードを書くことができます。

```csharp
// C# 12 活用例
using System;
using System.Collections.Generic;
using System.Linq;

// プライマリコンストラクタを持つレコード型。Javaのレコードに近い
public record CustomerInfo(bool IsVip, bool IsFirstTimeBuyer);
public record OrderDetails(double TotalPrice, string PromoCode);

public class AdvancedOrderService
{
    // 割引ルールを表現するインターフェース
    public interface IDiscountRule
    {
        double Apply(OrderDetails order, CustomerInfo customer);
    }

    // 割引ルールを具体的なクラスとして定義（戦略パターン）
    public class VipDiscount : IDiscountRule
    {
        public double Apply(OrderDetails order, CustomerInfo customer)
        {
            return customer.IsVip ? order.TotalPrice * 0.15 : 0.0;
        }
    }

    public class FirstTimeBuyerDiscount : IDiscountRule
    {
        public double Apply(OrderDetails order, CustomerInfo customer)
        {
            return customer.IsFirstTimeBuyer ? order.TotalPrice * (order.TotalPrice > 5000 ? 0.05 : 0.02) : 0.0;
        }
    }

    public class PromoCodeDiscount(string code, double rate) : IDiscountRule // C# 12 プライマリコンストラクタ
    {
        // プライマリコンストラクタの引数はフィールドとして自動的に利用可能
        public double Apply(OrderDetails order, CustomerInfo customer)
        {
            return order.PromoCode == code ? order.TotalPrice * rate : 0.0;
        }
    }

    // コレクション式で割引ルールを初期化 (C# 12)
    private readonly List<IDiscountRule> _discountRules = [
        new VipDiscount(),
        new FirstTimeBuyerDiscount(),
        new PromoCodeDiscount("SUMMER2024", 0.10)
    ];

    public double CalculateFinalPrice(OrderDetails order, CustomerInfo customer)
    {
        // LINQを使って、各ルールを順番に適用し、最大の割引額を計算
        double totalDiscount = _discountRules
            .Select(rule => rule.Apply(order, customer))
            .Max(); // Max() は空の場合は例外を投げるため、DefaultIfEmpty(0.0) などで対策するとより堅牢

        return order.TotalPrice - totalDiscount;
    }
}
```

**改善点とC# 12のメリット:**

*   **単一責任の原則**: Javaの例と同様に、`IDiscountRule`と具体的なルールクラスによって、ビジネスロジックが適切に分離されています。
*   **可読性と保守性**: `CalculateFinalPrice`メソッドが、割引ルールの適用と集約に集中しています。LINQを使うことで、データのコレクションに対する操作が非常に宣言的に記述でき、意図が明確になります。
*   **レコード型の活用**: C#の`record`型は、データ保持に特化したクラスを簡潔に記述でき、値の比較セマンティクス（値が同じなら等しいと判断）を提供します。Javaのレコードと目的は似ています。
*   **C# 12 プライマリコンストラクタ**: `PromoCodeDiscount(string code, double rate)` のように、クラス宣言と同時にコンストラクタの引数を定義できるようになりました。これにより、フィールドの宣言と初期化をさらに簡潔に記述できます。
*   **C# 12 コレクション式**: `_discountRules = [...]` のように、コレクションの初期化が非常にシンプルになりました。これは、リストや配列を生成する際の記述量を減らし、可読性を高めます。

#### コードレビューの心構えと実践的な作法

さて、具体的なコードの改善例を見ていただきましたが、ここからは「コードレビューの作法」についてお話しします。

##### レビューされる側として

1.  **謙虚な姿勢で受け止める**: 指摘は、あなたのコードをより良くするためのアドバイスであり、あなた自身への批判ではありません。感情的にならず、「学びの機会」と捉えましょう。
2.  **目的を理解する**: なぜそのように指摘されたのか、その背景にある「より良いコード」の原則（可読性、保守性、パフォーマンスなど）を理解しようと努めましょう。
3.  **不明点は質問する**: 分からないことや納得できないことは、遠慮せずに質問しましょう。「なぜそのようにすべきなのか？」「他に選択肢はないか？」など、具体的な質問をすることで、深い学びが得られます。
4.  **感謝を伝える**: レビューは時間と労力のかかる作業です。指摘してくれた人には、必ず感謝の気持ちを伝えましょう。「ありがとうございます。勉強になりました！」の一言が、今後の良好な関係を築きます。
5.  **改善策を自分で考える**: ただ修正するだけでなく、「なぜこの改善が必要なのか」「次からはどう書けばいいのか」を自分で考え、次回に活かす意識を持ちましょう。AIに相談するのも有効です。

##### レビューする側として（将来のあなたへ）

1.  **建設的なフィードバックを心がける**: 「ここがダメ」ではなく、「こうすればもっと良くなる」「なぜなら〇〇だから」と具体的に、理由を添えて伝えましょう。改善策の提案までできれば完璧です。
2.  **指摘はピンポイントに、優しく**: 批判的な言葉は避け、客観的な事実に基づいた指摘を。相手の成長を願う気持ちが伝わるようにしましょう。
3.  **良い点も褒める**: 改善点だけでなく、素晴らしいコードや工夫があれば、積極的に褒めましょう。モチベーション向上に繋がります。
4.  **目的を明確にする**: 「これはバグにつながる」「これは将来の保守性を損なう」など、指摘の目的を明確にすることで、相手も納得しやすくなります。
5.  **対話を重視する**: 一方的な指摘ではなく、疑問があれば質問を投げかけ、相手の意図を理解しようと努めましょう。コードの背景にある考え方を引き出すことで、より深いレビューができます。

## 2. Java vs C# 実装比較：最新機能でコードを洗練させる

AIの回答でも触れましたが、JavaとC#は、それぞれの言語特性と進化の方向性に応じて、コードをより洗練させるための最新機能を積極的に取り入れています。改めて、その魅力を比較してみましょう。

### Java 21の進化：簡潔さと表現力

Java 21では、特に以下の機能がコードの可読性・保守性向上に貢献します。

1.  **レコードパターン (Record Patterns)**:
    *   `switch` 式や `instanceof` 演算子と組み合わせて、レコード型のコンポーネントを直接パターンマッチングできるようになりました。これにより、複雑なオブジェクトの分解と条件分岐を簡潔に記述できます。
    *   **AIの例での活用**: 今回の例では直接使われていませんが、もし`DiscountRule`が複数のレコード型を引数に取る場合など、オブジェクトの構造に応じて処理を分岐させたい場合に非常に強力です。
    ```java
    // 例: もしルールが CustomerInfo と OrderDetails の組み合わせで決まる場合
    // switch (discountCondition) {
    //    case CustomerInfo(boolean isVip, _) && OrderDetails(double price, _)
    //        if (isVip && price > 10000) -> { /* VIP高額割引 */ }
    //    // ...
    // }
    ```

2.  **パターンマッチング for switch**:
    *   `switch` 式/文で、データ型に基づくパターンマッチングが可能になりました。これにより、`if-else if (instanceof)` のチェーンが解消され、より読みやすいコードになります。
    *   **AIの例での活用**: 各`DiscountRule`の実装を`switch`で分岐させることも可能ですが、AIの例ではポリモーフィズム（戦略パターン）を使っているため、`switch`の代わりに`stream().mapToDouble().max()`で抽象化されています。これはどちらも良い設計です。

3.  **シーケンスコレクション (Sequenced Collections)**:
    *   `List`, `Deque`, `SortedSet`といったコレクションに、順序付けされた要素へのアクセス（最初、最後）や逆順処理を標準化する新しいインターフェースが導入されました。
    *   **AIの例での活用**: 今回の例では直接的な利用はありませんが、もし割引ルールの適用順序が重要で、最初や最後のルールに特殊な処理が必要な場合などに役立ちます。

### C# 12の進化：さらにパワフルな記述

C# 12でも、開発者の生産性とコードの表現力を高める機能が多数導入されています。

1.  **プライマリコンストラクタ (Primary Constructors)**:
    *   クラスや構造体の宣言時にコンストラクタのパラメーターを直接定義できるようになりました。これにより、コンストラクタの宣言とフィールドの初期化が驚くほど簡潔になります。
    *   **AIの例での活用**: `public class PromoCodeDiscount(string code, double rate) : IDiscountRule`
        *   このように書くだけで、`code`と`rate`がクラスのスコープ内で利用可能なフィールドのように扱われます。ボイラープレートコードの削減に大きく貢献します。

2.  **コレクション式 (Collection Expressions)**:
    *   リスト、配列、スパンなどのコレクションを、簡潔な構文 `[...]` で初期化できるようになりました。複数の要素や他のコレクションを組み合わせることも可能です。
    *   **AIの例での活用**: `private readonly List<IDiscountRule> _discountRules = [...]`
        *   従来の`new List<IDiscountRule> { ... }`と比較して、より視覚的にすっきりとコレクションを表現できます。

3.  **ラムダ式の既定値パラメータ (Default Parameters for Lambda Expressions)**:
    *   ラムダ式のパラメータに既定値を設定できるようになりました。これにより、より柔軟な関数定義が可能になります。
    *   **AIの例での活用**: 今回の例では直接使われていませんが、もし`Apply`メソッドが追加のオプションパラメーターを持つようになった場合などに、ラムダ式でルールを定義する際に役立つでしょう。

JavaもC#も、開発者がより少ないコードでより多くのことを表現し、かつそのコードが読みやすく、保守しやすいものであることを目指して進化しています。これらの最新機能を積極的に学習し、日々の開発に取り入れていくことが、皆さんの「良いコード」への探求心を刺激するはずです。

## 3. 若手への一言：明日から使える「お作法」

A君、そして若手の皆さん。ここまで私の思考、AIとの対話、具体的なコード例を見てきてどう感じましたか？

「動けばいい」という段階を卒業し、「保守性の高いコード」を書くというのは、まるで料理の腕を上げるようなものです。最初はレシピ通りに作って「食べられる」ものを作る。しかし、熟練してくると、素材の味を活かし、見た目も美しく、食べる人のことを考えた「美味しい料理」が作れるようになります。コードも全く同じです。

明日からすぐに実践できる「コードレビューのお作法」をいくつかお伝えしましょう。

### 1. レビュー依頼時の「お作法」

*   **レビュー目的を明確に**: 「〜の機能実装です。特に〇〇の部分は、より良い書き方がないか見ていただきたいです」のように、何を見てほしいのか、何に懸念があるのかを具体的に伝えましょう。
*   **変更点を自分でまとめる**: Pull Request (PR) の説明文に、「今回の変更で解決した課題」「主要な変更点」「特に見てほしい箇所」「自己レビューでの懸念点」などを箇条書きで記載しましょう。レビューアの負担を減らし、建設的な議論に繋がりやすくなります。
*   **小さくこまめに依頼する**: 一度に大量のコードをレビュー依頼するのではなく、機能単位や小さな修正ごとにPRを分けましょう。レビューアが集中して確認でき、品質も向上します。

### 2. レビューコメントへの「お作法」

*   **まずは感謝を伝える**: 指摘されたら、「レビューありがとうございます！助かります」と一言添えましょう。心理的なハードルが下がり、良好な関係を保てます。
*   **不明点は遠慮なく質問**: 「〜の部分ですが、なぜこのように修正すべきなのでしょうか？理由を教えていただけますか？」「A案とB案で迷ったのですが、今回はA案を選んだ背景を説明します」など、自分の考えを伝えつつ、積極的に質問しましょう。これが一番の学びの機会です。
*   **修正内容を具体的に伝える**: 修正したら「〇〇のように修正しました」と報告するだけでなく、「ご指摘いただいた点について、〇〇の理由からA案で修正しました。いかがでしょうか？」と、修正意図を添えることで、レビューアも再確認しやすくなります。
*   **全てを鵜呑みにしない**: レビューコメントは「提案」です。必ずしも全てが正しいわけではありませんし、チームやプロジェクトの文脈によっては、別の選択肢が最適なこともあります。不明な点、納得できない点は議論を通じて深掘りし、最終的には自分で判断する力を養いましょう。

### 3. 日常の開発での「お作法」

*   **良いコードを真似る**: チーム内の「きれいなコード」「分かりやすいコード」を積極的に読み、良い書き方を吸収しましょう。先輩のコードが最高の教材です。
*   **設計パターンを学ぶ**: 今回の「戦略パターン」のように、ソフトウェア開発には先人たちの知恵が詰まった「設計パターン」が存在します。これらを学ぶことで、より堅牢で柔軟なコードを書くための引き出しが増えます。
*   **「なぜ？」を常に問う**: 自分が書いたコードに対しても、チームメイトのコードに対しても、「なぜこの書き方を選んだのだろう？」「他に方法はなかったか？」と自問自答する習慣をつけましょう。
